DIRETTIVE GENERALI DELLA WEBAPP LLM-MASTER

l'app simula una giocata di gioco di ruolo tradizionale ma con un master basato su LLM. Per quest app, il sistema di gioco sottostante è Call of Cthulhu (ovvero il sistema basic basato su d100)

l sistema deve essere implementato come applicazione web con backend in Node.js e frontend in Vue.js
Il sistema deve utilizzare JavaScript come linguaggio di programmazione sia per backend che frontend
Il sistema deve persistere tutti i dati su file system in formato JSON o Markdown
il sistema deve usare usa Socket.io per gestire chat multi-utente, aggiornamenti stato turno, toast, e typing effect
Il sistema deve usare JWT stateless (fisso per 24h) per l'autenticazione

Il sistema deve richiedere autenticazione tramite login per accedere al frontend
Il sistema deve utilizzare l'email come identificatore univoco per ogni utente

Il sistema deve garantire agli utenti con ruolo "player" l'accesso a: Login/Logout, Lobby, Session, Profile
Il sistema deve garantire agli utenti con ruolo "admin" l'accesso a: Login/Logout, Profile, Manager Players, Module Manager, Table Manager
Il sistema deve permettere agli utenti autenticati di effettuare logout, modificare la propria password, il proprio nome visualizzato
Il sistema deve permettere solo agli utente con ruolo player di eliminare il proprio account (il sistema deve impedire a un utente admin di eliminare il proprio account; un admin non può avere accountState="disabilitato" o "eliminato")
Un admin non è un giocatore (non può entrare in sessione). E' un account speciale che si occupa solo di gestire le cose. 


GESTIONE ACCOUNT PLAYER
Il sistema deve permettere agli admin di visualizzare la lista completa dei giocatori iscritti (vista Manager Players), mostrando per ogni giocatore: Email, Nome, Data di iscrizione, Stato account

Il sistema deve permettere agli admin di invitare nuovi giocatori, e di eliminare giocatori esistenti

Alla pressione del pulsante invita l'account verrà registrato come "invited". 
L'utente invitato dovrà usare email e codice di invito per autenticarsi, ma sarà invitato a cambiare immediatamente la password. Dopo questo passo l'account diventerà attivo.


GESTIONE MODULI AVVENTURA
Il sistema deve permettere agli admin di creare nuovi moduli avventura, modificare moduli avventura esistenti, e di eliminare moduli avventura


GESTIONE TAVOLI
Il sistema deve permettere agli admin di creare un nuovo tavolo
Durante la creazione di un tavolo, il sistema deve richiedere all'admin di selezionare un modulo avventura, di selezionare una lista di giocatori e  selezionare un modello LLM da una lista predefinita
Il sistema deve permettere agli admin di aggiungere o sostituire giocatori in un tavolo, di riportare un tavolo da stato "disabled" a stato "active" tramite l'aggiunta di un giocatore, o di archiviare un tavolo.
Il sistema deve impostare come pianificazione di default la data/orario di creazione dell'ultimo personaggio
l sistema deve permettere all'admin di impostare data, orario e durata della prossima sessione
In fase di betatest, il sistema deve fornire una funzione per cancellare tutti i tavoli. 

Il sistema userà Ollama per l'accesso alla LLM. Quindi la lista dei modelli può essere ottenuta interrogando ollama con il comando list.


GESTIONE SALA DI ATTESA (LOBBY)

Il sistema deve visualizzare nella lobby tutte le table a cui l'utente corrente è stato invitato.
Il sistema deve permettere a un giocatore invitato di creare il proprio personaggio quando il tavolo è in stato "active"
Il sistema deve permettere a un giocatore di entrare in sessione quando la data e l'orario pianficato sono giunti.


GENERAZIONE DEL PERSONAGGIO
Il sistema deve permettere di generare tutte le volte che si vuole le 8 caratteristiche del personaggio (FOR, COS, etc.) più il valore di Fortuna, assegnando casualmente ad esse dei valori da un pool (40, 50, 50, 50, 60, 60, 60, 70, 80) 

Il sistema calcola e mostra i valori derivati:
- Punti Ferita (PF) = (COS + TAG) / 10 arrotondato per difetto
- Punti Magia (PM) = POT / 5 arrotondato per difetto
- Sanità (SAN) = POT
- Bonus Danno: calcolato da FOR + TAG secondo la tabella: 
FOR+TAG in [2-64] => Bonus Danno=-2
FOR+TAG in [65-84] => Bonus Danno=-1
FOR+TAG in [85-124] => Bonus Danno=0
FOR+TAG in [125-164] => Bonus Danno=+1d4
FOR+TAG in [165-204] => Bonus Danno=+1d6

- Movimento (MOV): 
se FOR e DES sono entrambe < TAG => mov = 7; 
se una tra FOR e DES >= TAG => mov = 8;
se sia FOR che DES >= TAG => mov = 9;

Le abilità derivano dalla professione scelta.
Le professioni e le relative abilità si leggono da file 
I valori base delle abilità di professione sono impostati a 40%. 


SESSIONE DI GIOCO
Il sistema deve avviare un timer "avvio sessione" di 5 minuti quando il primo giocatore si collega a un tavolo in stato "open", impostando lo stato della sessione a `primo-giocatore`
Il sistema deve impostare lo stato del tavolo a "playing" quando il timer "avvio sessione" scade o quando tutti i giocatori invitati sono collegati. Quando lo stato del tavolo passa a "playing" il custode per iniziare, impostando lo stato della sessione a `sessione-iniziata`
Il sistema deve considerare temporanee tutte le disconnessioni che avvengono dopo che lo stato è passato a "sessione-iniziata", mantenendo le attività anche quando alcuni giocatori si disconnettono (temporaneamente).
Il sistema deve permettere ai giocatori che si riconnettono di recuperare i messaggi persi durante la disconnessione. Questi saranno visualizzati normalmente in chat al momento della riconnessione, ma con un marker speciale "da recuperare".
Il custode deve risolvere le situazioni in cui un giocatore di turno si disconnette, spostando il focus sua qualche altra situazione.
Il sistema può mettere in pausa la sessione quando tutti i giocatori si disconnettono o se c'è un problema tecnico. Quando è in pausa il ciclo del custode si ferma e i timer (proattività e silenzio) vengono messi in pausa.
Il sistema deve mantenere un registro dei presenti (non tenendo conto di eventuali ritardi o disconnessioni premature)
Il sistema deve permettere ai giocatori di indicare la propria volontà a terminare la sessione. Se la somma dei giocatori disconnessi e di quelli ancora presenti che hanno indicato di voler terminare è almeno la metà dei presenti durante la sessione (vedi registro presenti), allora la sessione passa in stato "In chiusura". Il Custode deve procedere alla fase "Chiusura sessione".
Il sistema deve impostare stato "Terminata" quando il Custode saluta tutti.

Area Chat
Il sistema deve visualizzare nella chat solo le conversazioni tra PG e tra PG e Custode
Il sistema deve visualizzare i messaggi di connessione/disconnessione o problemi tecnici come toast temporanei di breve durata
Il sistema deve visualizzare i risultati di un tiro di dadi come toast temporanei di media durata
Il sistema deve fare un auto-scroll all'ultimo messaggio quando arriva nuovo messaggio
Il sistema deve comunque garantire lo scroll manuale disponibile per leggere storia
Il sistema deve garantire al giocatore di selezionare il proprio colore per le bolle messaggio. Il cambio colore aggiorna retroattivamente tutte bolle già in chat.
Il sistema, per i messaggi del custode, mostra un "..." prima di scrivere il testo e poi applica un effetto macchina da scrivere
Il sistema consegna i messaggi marcati come sussurri solo al giocatore target (sarà visibile solo nella sua area chat).
   
Area Stato Giocatore
Il sistema gestisce lo stato di ogni giocatore in base al contesto della giocata.

BUFFER MESSAGGI - TRIGGER DI ELABORAZIONE
Il sistema deve processare immediatamente la dichiarazione svolta in modalità 'mio-turno-libero'
Il sistema deve processare immediatamente l'esito di una prova svolta in modalità 'mio-turno-prova'
Il sistema deve raccogliere le dichiarazioni in gioco-libero in un buffer, per poi elaborarle in un unico batch.
Il sistema può avviare un timer "di silenzio" (30 secondi) per stimare se la conversazione è terminata e i giocatori aspettano una risposta dal master. 
Il sistema può usare una light LLM per processare il buffer di gioco-libero in background per "annotare" i messaggi dei giocatori con delle etichette utili sia a stabilire quando processare che nella fase di processo
Il sistema deve processare il buffer di gioco-libero quando il timer "di silenzio" scade , oppure quando il buffer si riempie (la dimensione del buffer è un parametro di ambiente), o ancora quando le annotazioni dei messaggi indicano che i giocatori hanno finito di dichiarare.
Il sistema deve cancellare il timer "di silenzio" attivo quando processa il buffer
Il sistema deve svuotare completamente il buffer dopo ogni elaborazione

STATO DEL MONDO
Il Custode deve consultare il documento Stato del Mondo per conoscere dettagli della scena in corso
Il Custode deve aggiornare il documento Stato del Mondo quando cambia qualcosa di attinente nelle scene
Il sistema deve permettere la coesistenza di più gruppi di PG contemporaneamente
Il sistema deve permettere l'esistenza di più scene/sottoscene contemporaneamente (una per gruppo)
Il custode deve mantenere il focus narrativo su una sola scena alla volta
Il sistema deve raggruppare nello stesso gruppo i PG che si ricongiungono nella stessa scena
Il Custode deve aggiornare il documento Stato del Mondo per tenere conto dell'eventuale suddivisione dei PG in vari gruppi
Il Custode deve tenere conto della suddivisione in gruppi per destinare messaggi e gestire turni
    
Il sistema deve strutturare l'avventura in scene sequenziali.
Il sistema prepara una scena estraendo le informazioni chiave dal modulo avventura.


CICLO DI VITA DEL CUSTODE
Il comportamento del custode è gestito tramite un ciclo di vita procedurale strutturato in fasi. La Fase 1 del ciclo di vita inizia automaticamente nel momento stesso in cui la sessione va in stato "sessione-iniziata". Il ciclo di vita può essere messo in pausa.
Le decisioni e le esternazioni del custode nelle varie fasi è gestito tramite LLM
Il custode può usare diverse LLM con capacità e tempi di risposta differenti per gestire diverse fasi e momenti (distinguiamo in light LLM e heavy LLM).
Tutte le comunicazioni ai giocatori devono essere gestite da una heavy LLM.
Il custode può usare un timer "proattività" (5 min) per misurare il tempo di inattività in chat e aggiungere stimoli al gioco. Il timer si avvia in Fase 3, e si interrompe in Fase 4. 
Il sistem reagisce al timer "proattività" tornando in Fase 3 e aggiungendo dettagli e opportunità per i PG. 

Il sistema deve registrare dati rilevanti al testing del sistema in dei file di log. Dati rilevanti includono connessione/disconnessione di giocatori, messaggi in chat, dati del buffer, fasi e decisioni del custode, eventi dei timer.

Il sistema usa delle LLM per generare dei file JSON. Il sistema deve prevedere un meccanismo di retrial per garantire robustezza quando il modello genera output malformato.
Se una chiamata ad una LLM va in timeout per un certo numero di volte consecutive, il sistema segnala un errore tecnico (tramite toast message) e si mette in pausa.

Il sistema può prevedere un meccanismo di compressione/troncamento del contesto per l'ottimizzazione della dimensione del prompt per la LLM.
L'uso di una scena al posto di fornire l'intero modulo avventura fa parte di queste strategie. Al posto di passare l'intera scheda PG in JSON, si potrebbe pensare ad un "sintetizzatore" che riduce la scheda ad una sola riga di testo.

Quando i PG si dividono in più gruppu, il custode interagisce con un solo gruppo per volta. Questo si chiama gruppo in focus.
Il sistema usa un timer "proattività" per gestire la conversazione con il gruppo in focus per valutare il bisogno di intervenire con nuove informazione o stimoli. 
Il custode cercherà di alternare tra i gruppi,, rispettando però delle regole di gestione della scena.



SCHEMA DATI PER UN ACCOUNT
email: string - Email utente (ID univoco) [obbligatorio] [email valida]
name: string - Nome visualizzato [obbligatorio]
password: string - Password hash [obbligatorio]
role: enum - Ruolo utente [obbligatorio] [player|admin]
accountState: enum - Stato account [obbligatorio] [invited|attivo|disabilitato|eliminato]
registrationDate: string - Data registrazione [obbligatorio] [ISO 8601]

Esempio: 
{
  "email": "alice@example.com",
  "name": "Alice Wonderland",
  "password": "$2b$10$...", 
  "role": "player",
  "accountState": "attivo",
  "registrationDate": "2026-03-15T10:30:00Z"
}

ENUM VALORI VALIDI PER LO STATO DI UN ACCOUNT:
Invited: Giocatore invitato ma non registrato
attivo: Account funzionante (solo gli account attivi possono essere inclusi in un tavolo)
disabilitato: Utente ha eliminato il proprio account
eliminato: Admin ha eliminato l'utente

STRUTTURA FILE DI UN TAVOLO

ogni tavolo genere una cartella data/tables/{table-id}/
che contiene:
	- table.json (che contiene info sul tavolo)
	- characters (con le schede dei PG)
	- diary.txt (file di testo che riassume i fatti)
	- world_state.json (che contiene lo stato corrente del mondo, le scene aperte, il focus di scena e il capitolo del modulo a cui i PG sono arrivati)
	- una sottocartella sessions che contiene i dati di sessione
	- una sottocartella active_scenes che contiene tutti le scene ancora attive
	- una sottocartella closed_scenes che contiene tutti le scene chiuse
	- una sottocartella logs che contiene tutti i file log_session



SCHEMA DATI PER UN TAVOLO
- id: string - Identificatore univoco tavolo [obbligatorio] [UUID]
- moduleId: string - Riferimento modulo avventura [obbligatorio]
- heavy-llmModel: string - Modello LLM selezionato per i task impegnativi [obbligatorio]
- light-llmModel: string - Modello LLM selezionato per task secondari [opzionale]
- state: enum - Stato tavolo [obbligatorio] [active|ready|open|playing|disabled|archived]
- invitedPlayers: array<string> - Email giocatori invitati [obbligatorio] [min: 1]
- plannedSession: object - Pianificazione prossima sessione [opzionale]
  - date: string - Data sessione [obbligatorio] [ISO 8601 date]
  - time: string - Orario sessione [obbligatorio] [HH:MM]
  - duration: number - Durata in minuti [obbligatorio]
- custodeStarted: boolean - Custode ha avviato sessione [obbligatorio] [default: false]

I tavoli sono persistenti in data/tables/{table-id}/table.json

Esempio
{
  "id": "tbl_a1b2c3d4",
  "moduleId": "mod_masks_nyarlathotep",
  "heavy-llmModel": "claude-sonnet-4",
  "light-llmModel": "claude-sonnet-4",
  "state": "ready",
  "invitedPlayers": [
    "alice@example.com",
    "bob@example.com",
    "charlie@example.com"
  ],
  "plannedSession": {
    "date": "2026-04-05",
    "time": "20:00",
    "duration": 180
  },
  "custodeStarted": false
}

ENUM VALORI VALIDI PER STATE OF TABLE:
- `active`: Tavolo creato, non tutti i giocatori hanno aderito e creato PG
- `ready`: Tutti i giocatori hanno creato PG, pronta la pianificazione prossima sessione
- `open`: Data/orario pianificati sono passati, si può entrare in sessione
- `playing`: tutti i giocatori sono in sessione, o comunque il custode ha avviato la sessione
- `disabled`: Un giocatore invitato è stato eliminato
- `archived`: Tavolo eliminato

      startingValue: number - Valore iniziale, uguale a POT [obbligatorio]

    build: number - Corporatura, calcolato da FOR+TAG [obbligatorio] [-2, -1, 0, 1, 2, ecc.]
    movimento: number - Valore di movimento [obbligatorio] [7, 8, o 9]

      psicologia: number - Abilita Psicologia, valore base 10 [obbligatorio] [1-100]
      credito: number - Abilita Nota di Credito, valore base 10 [obbligatorio] [1-100]
    specialistiche: array - Lista abilita specialistiche/professionali [obbligatorio]
      [elemento array]
        nome: string - Nome dell'abilita [obbligatorio]
        valore: number - Valore abilita [obbligatorio] [1-100]

Le schede dei PG sono file persisenti in data/tables/{table-id}/characters/{character-id}.json

SESSIONE DI GIOCO

La sessione di gioco ha uno stato di cui i valori validi sono:
- `custode-pronto`: In attesa dei giocatori
- `primo-giocatore`: Primo giocatore collegato, timer avviato
- `sessione-iniziata`: Tutti collegati o timer scaduto
- `in-pausa`: Tutti i player si sono collegati o il custode ha un problema tecnico
- `in-chiusura`: Maggioranza ha votato "è tardi"
- `terminata`: Custode ha salutato tutti


Ogni giocatore in sessione ha uno stato:
- `turno-custode`: Custode sta comunicando
- `gioco-libero`: Tutti i PG di un gruppo possono chattare e dichiarare
- `mio-turno-libero`: È il turno del giocatore di dichiarare
- `mio-turno-prova`: È il turno del giocatore di tirare i dadi
- `fuori-turno`: Turno di un altro giocatore del proprio gruppo
- `fuori-scena`: Turno di altro gruppo

Queste informazioni persistono in un file data/tables/{table-id}/sessions/session{session-id}.json
      
SCHEMA DATI PER UNA SESSIONE
- sessionId: string - Identificatore univoco sessione [obbligatorio] [UUID]
- sessionNumber: number - Numero progressivo sessione per questo tavolo [obbligatorio]
- state: enum - Stato sessione [obbligatorio] 
  [custode-pronto|primo-giocatore|sessione-iniziata|in-pausa|in-chiusura|terminata]
- custodePhase: string - Fase corrente del ciclo Custode [opzionale] 
  ["fase-1"|"fase-2"|"fase-3"|"fase-4"|"fase-4a"|"fase-4b"|"fase-4c"|"fase-5"|"fase-5a"|"fase-5b"|"fase-5c"|null]
- focusGroupId: string - Gruppo attualmente in focus [opzionale]
- startedAt: string - Timestamp inizio sessione [opzionale] [ISO 8601]
- endedAt: string - Timestamp fine sessione [opzionale] [ISO 8601]
- registroPresenti: array<string> - Email dei giocatori che si sono collegati almeno una volta [obbligatorio]
- players: array<object> - Stato corrente di ogni giocatore [obbligatorio]
  - email: string - Email giocatore [obbligatorio]
  - playerState: enum - Stato di gioco [obbligatorio]
    [turno-custode|gioco-libero|mio-turno-libero|mio-turno-prova|fuori-turno|fuori-scena]
  - connected: boolean - Connesso via WebSocket [obbligatorio]
  - voteTardi: boolean - Ha votato "è tardi" [obbligatorio] [default: false]
  - lastSeen: string - Ultimo timestamp di attività [opzionale] [ISO 8601]
  - missedSince: string - Timestamp disconnessione (per calcolo messaggi "da recuperare") [opzionale] [ISO 8601]
- pianoAzione: object|null - Piano azione parziale o completo della fase 4 corrente [opzionale]
- lastMessageId: string - ID ultimo messaggio in chat (per gestione riconnessione) [opzionale]
    

I messaggi dei giocatori possono essere annotati con questi tag:
[domanda al custode]
[dichiarazione]
[discutendo tra PG]
[fuori ruolo]


SCHEMA DATI PER UNA SCENA
  id_scena: string - Identificatore univoco scena [obbligatorio] [UUID]
  contesto_dove: string - Contesto generale dove si svolge la scena [obbligatorio]
  contesto_quando: string - Contesto temporale quando si svolge la scena [obbligatorio]
  location: string - Descrizione dettagliata della location [obbligatorio]
  npcs: string - Descrizione dei PNG presenti nella scena [opzionale]
  opportunita: array - Lista delle opportunita disponibili nella scena [opzionale]
    [elemento array]
      descrizione: string - Descrizione dell'opportunita [obbligatorio]
      prova: string - Caratteristica o abilita da testare [obbligatorio]
      difficolta: string - Livello di difficolta [obbligatorio] ["facile", "normale", "difficile"]
      esito_successo: string - Cosa accade in caso di successo [obbligatorio]
  minacce: array - Lista delle minacce presenti nella scena [opzionale]
    [elemento array]
      descrizione: string - Descrizione della minaccia [obbligatorio]
      trigger: string - Cosa scatena la minaccia [obbligatorio]
      conseguenza: string - Cosa accade quando si attiva [obbligatorio]
  indizi: array - Lista degli indizi scopribili nella scena [opzionale]
    [elemento array]
      descrizione: string - Descrizione dell'indizio [obbligatorio]
      metodo: string - Come puo essere scoperto l'indizio [obbligatorio]
      prova: string - Caratteristica o abilita da testare [opzionale]
      difficolta: string - Livello di difficolta [opzionale] ["facile", "normale", "difficile"]
      informazione: string - L'informazione rivelata dall'indizio [obbligatorio]
      porta_a: string - Cosa sblocca questo indizio [opzionale]
 summary: string - riepilogo della narrativa di questa scena una volta chiusa [opzionale]
 
Il file scene sono persistenti nelle cartella
data/tables/{table-id}/active_scenes se la scena è ancora attiva
data/tables/{table-id}/closed_scenes se la scena è chiusa


il file diary.txt è un file di testo puro. Sarà aggiornato dal custode nell'arco delle scene e delle sessioni.
